## 2026-07-03 prompt 內寫「不要派背景 agent」擋不住，可靠解法是 SendMessage 叫醒
情境：某 repo session，三個派工 agent prompt 內都有「不要派背景 agent、不要用 run_in_background」，仍然自派背景工作後停在「等通知」，最終訊息不是回報。

建議寫回：30-TEMPLATES.md 通則（把復原流程寫成固定條目）；觀察中。

## 2026-07-06 派工 agent 重跑後用不同結論覆寫產出，口頭報告與磁碟不一致

## 2026-07-07 bash `test -e`/`[ -f ]` 配 &&/|| 的 loop 計數在本 shell 不可靠，用 python 核對

## 2026-07-09 RCA agent 被票面假設錨定，停在第一個自洽解釋
情境：某根因分析任務，派工 agent 順帶分析根因，review 後發現結論非主因——grep 關鍵字全為「證實既有假設」而挑，錯誤分支鏈路一自洽就收工，沒往上游追偵測邏輯。
錯誤：比較 predicate（`===`、容差）只確認函式存在沒點進去讀；同一實體的 payload 數值（例如座標精度不同）沒主動 diff；「合理但未驗證」的紅鯡魚機制寫成定論。直到領域專家點名機制才破案。
修正：五條 RCA 紀律（兩問題分開查／必讀 predicate 本體／payload 數值主動 diff／跑反證問句／未證實標推測）＋證據型別要求＋反證派工觸發條件（結論與票面假設一致、或將進 report 定論時）。
建議寫回：通用性觀察中——若他處再現，升格 30-TEMPLATES 研究/審查模板。

## 2026-07-11 分發鏈反向漏水：拷貝拿到 feature 沒回流正典，雙副本各對一半
情境：對齊某 playbook 的正典與其 plugin 拷貝的 4 處分歧（附件下載上限與型別限制兩側不同）。
錯誤：預設「正典對、拷貝漂了」，實際相反——較寬的行為是刻意 feature，直接改在拷貝側、沒回流正典；連正典附帶的腳本都停在舊行為。文件宣稱誰是正典，靠猜會猜錯。
修正：(1) 裁定分歧一律以「腳本程式碼＋git 史」為證據，不以「哪份叫正典」定勝負；(2) 對齊後讓兩份逐位元組一致（diff 空 = 可機械檢查 drift）；(3) 分發鏈是雙向紀律——改拷貝側的 feature 也必須同步回正典，不只正典→拷貝。
建議寫回：分發／vendoring 類 repo 的同步紀律段；觀察中。

## 2026-07-13 驗收只驗「一致性」抓不到「一致地錯」——判定邏輯要 truth-table＋對抗審查
情境：某 matching/correlation 功能，第二輪自驗全綠（複跑作者測試＋文件 read-back），reviewer 仍抓出兩個 HIGH：selector 零命中 fall-through 到唯一候選、per-interaction registry 使延遲 callback 跨界無法配對。
錯誤：(1) 測試由同一設計心智從 spec 正面條款推導，沒枚舉 {selector 有/無}×{0/1/>1 命中} 全表，「有 selector 但零命中」整格缺失；(2) read-back 驗「文件與程式一致」，兩者一致地錯照樣全綠——流程裡沒有任何一步對抗地問「什麼輸入會讓設計出錯」；(3) 實作 agent 回報過「repo 無真實 fixture、端到端靠 synthetic 資料」，風險有讀到但沒行動（該向使用者要真實樣本）；(4) 判定條文有兩解，返工成本高卻沒追問。
修正：matching/correlation 類邏輯 push 前：(1) 每個證據維度×{缺席,0,1,>1} 機械枚舉測試，不從 spec 案例清單推導；(2) 派 fresh 對抗審查 agent（審查模板）建構失效情境，驗正確性而非一致性；(3) 「fixture 不覆蓋本功能」視為 blocker 級訊號；(4) 判定規則語義有兩解就先問。
建議寫回：30-TEMPLATES 審查模板／10-DISPATCH §5（觀察中）。

## 2026-07-13 review 抓到缺陷卻判錯嚴重度——「不崩潰」不等於 low，「可能」不准直接交卷
情境：某 MR review，兩軸獨立命中同一行空 id 缺陷，皆判 PLAUSIBLE/low（「空轉非崩潰」）；外部 reviewer 用 repo 現成 fixture 釘成 CONFIRMED/Major——空轉正是讓修復目標（刪 history）靜默失效。
錯誤：(1) 嚴重度用「機械傷害」標尺（會不會崩），沒問「這條路徑的目的還達成嗎」；(2) 推理到「id 可能為空」就標 PLAUSIBLE 收工，沒去 grep repo fixtures 做一次具體值 trace（一步之遙）；(3) 兩軸交會同一位置只並列呈報，沒做合軸檢查，關鍵合成落在隔離的縫裡。
修正：三條判準——goal-defeat=Major、PLAUSIBLE 釘死步驟（去 fixtures/mocks/log 做具體值 trace）、交會點第三次合軸檢查。
建議寫回：審查嚴重度判準；通用性觀察中——若非 review 情境也再現「可能就交卷」，升格 30-TEMPLATES 審查模板。

## 2026-07-14 port 打錯目標產品：官方機制存在 ≠ 消費者實際在跑

## 2026-07-17 把「官方文件說的」直接寫成「已生效」——執行中的 session 認不到新 agent 定義檔
情境：建 `~/.claude/agents/` 把派工表固化成定義檔。官方文件寫「自動偵測檔案變更、數秒生效、不必重啟」，實作 agent 據此在 README 與 10-DISPATCH 寫下「已覆蓋內建 Explore 釘死 sonnet」。
錯誤：該 session 派 `subagent_type: verifier` 直接回 `Agent type not found`；且該 session 曝露的 `Explore` 仍是內建版（description／tools 都與新定義檔不符）＝覆蓋未生效。文件把「檔案已建立」寫成「行為已生效」，未來 session 讀了會照做然後報錯。read-back agent 抓到並釘死（實測證據＋確切行號）。

建議寫回：40-MAINTENANCE §5（規則與現實衝突）已涵蓋處理原則；本條補充的是「宣稱 vs 實測」的**觸發時機**。觀察中。

## 2026-07-25 三模型同題盲測：紀律條款拉得平「表面合規」，拉不平「自發查證」
情境：某 MR 分析任務用同一 prompt（模板＋RCA 紀律）派 opus/sonnet/haiku 各分析同一個 MR，fresh-context opus 盲評五軸。
錯誤：haiku 只用 2 次工具呼叫（讀原始資料＋寫檔）就交卷，沒進原始碼、沒跑反證，用「合理敘事」補洞——立了被原始碼直接否定的錯誤前提（把長期既有的 enum 說成新增）；但結構／模板／未確認標註全合規（結構分 8.5 vs opus 9.5）。盲評：opus 9.4 > sonnet 9.1 >> haiku 7.4；sonnet 耗時反而最長（17.7 分 vs opus 7.3 分），品質貼近 opus。
修正：prompt 裡的「行為要求」（必須點進 predicate 本體）對弱模型無強制力，要轉成「產出物要求」才會被執行——模板加必填 Evidence log 節（列出讀過的原始碼 檔案:行號 ≥N 條＋反證問句的答案），或 haiku 產出後必配 sonnet read-back 對原始碼核對（錯前提正是 grep 一次就否證的類型）。sonnet 對此類分析任務是可用預設；opus 的獨有增值在「概念層洞察」，正是 20-JUDGMENT §6 說制度補不了的那部分。
建議寫回：n=1 觀察中——若 3~5 個同類任務重跑同向，升格 30-TEMPLATES（分析模板加 Evidence log 必填節）＋10-DISPATCH §1（haiku 條件放寬為「配 read-back 的初稿工」）。

## 2026-07-25 驗證輪（n=5）坐實模型階梯；「硬配額式查證要求」對弱模型反噬，逃生口版有效
情境：承前條 n=1 盲測，加跑 4 個 MR × 4 臂（opus／sonnet／haiku／haiku+Evidence log），每個 MR 獨立盲評。

## 2026-07-25 派工 agent「spawn 即死」新型態：0 工具呼叫、數秒結束、回音式最終訊息
情境：某 webservice 專案連續開發，implementer 派工兩次首輪夭折——最終訊息分別是樣板指令文字與「讓我先讀 spec」開場白，工具呼叫數 0、耗時 4~17 秒。

## 2026-07-26 對 append/prepend-only 檔案寫死行號，行號在同一 session 內就腐爛兩次
情境：某知識庫首次 lint。subagent 產出的報告以 `log.md:26/:36/:55` 標定 finding；我隨後在該檔頂端 prepend 一則更正條目（該檔規範是 prepend-only），報告裡**所有** log 行號整批位移 16 行，驗收 agent 逐一點開才抓到。修完再 prepend 第二則，又位移一次。
錯誤：兩層。(1) 對「新內容從頂端進來」的檔案用行號當錨點，等於寫下保證會過期的引用；(2) 想用「排除整個 log 檔」當重算配方，但該檔同時含**真的**導覽連結與**引述式**提及，排除整檔會砍掉真連結（實測 4 → 3）。另外自己加的計數註記寫「總共 8 個」，而註記本身引述了該連結文字，把總數推成 9——註記自我證偽。
修正：對 append/prepend-only 檔案（log、CHANGELOG、HANDOFF 之類）一律**以條目標題錨定**，不寫行號；需要保留歷史行號時明標「YYYY-MM-DD 當時位於 :N」。計數類斷言不要寫進會被自己改動的檔案，改為列舉權威站點清單。修正順序也要注意：**先**把引用改成穩定錨點，**再**動那個檔案的頂端。
建議寫回：20-JUDGMENT §5（品質底線加一條：引用錨點的穩定性也要驗——不只驗「現在指得到」，要驗「之後還指得到」）；n=1，觀察中。

## 2026-07-27 用 git 驗了「A 成立」，就把附帶的因果故事 B 一起當已驗證轉述
情境：某知識庫補漏。subagent 回報「某票的修正只在 release 分支、正線沒有，導致連續辨識第 2 輪起送出舊的 session 資料」。我用三條 git 指令驗了「未合併」為真，然後把整段（含因果）當成 CONFIRMED 報給使用者，還說「下一次切 release 會把缺陷帶回去」。
錯誤：我驗的是**機械事實**（某符號在 A 分支有、B 分支沒有），沒驗**因果宣稱**（缺這行會造成什麼）。後者才是使用者會拿去做決定的部分。事後專門的反證 agent 推翻它：那個 settings key 全 repo 零讀取者（4 個出現點全是寫入端），程式自己的請求路徑根本不讀它、直接取記憶體結構；而且既有的刷新路徑每次啟動辨識都會無條件跑，所以根因更可能是**時序**而不是**缺失**；「第 2 輪起」在程式碼裡完全推不出來（無輪次計數）。
修正：一份回報裡不同強度的宣稱要**拆開各自驗證**——「X 不在分支上」與「缺 X 會怎樣」是兩個命題，前者 grep 可證，後者要追消費端。特別是「缺少某個發布／同步呼叫」型的根因，必檢查三件事：(1) 那個被寫入的目標**有沒有讀者**；(2) 有沒有**其他既有路徑**也會做同一件事；(3) 宣稱的觸發條件（「第 N 次才錯」）在程式碼裡**有沒有對應的狀態**。三者任一答不出來就只能標 PLAUSIBLE。
建議寫回：20-JUDGMENT §2（Definition of Done 的「研究」類加一條：一份結論若含多個強度不同的宣稱，驗收要逐一標強度，不得以最強證據覆蓋全段）；n=1，觀察中。
