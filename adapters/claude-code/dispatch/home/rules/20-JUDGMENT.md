# 判斷力守則（Judgment Rubrics）
<!-- last-updated: 2026-07-03 | 每節都有：判準 → 正例 → 反例。照著核對，不要憑感覺。 -->

---

## 1. 何時直接用強模型（不要先試便宜的）

**判準**：任務輸出是「判斷」而非「執行」時——架構選型、安全結論、模糊需求的解讀、
多方案取捨——直接派 opus，跳過 haiku/sonnet。可從 sonnet 起跳的執行型任務只有兩類：
搜尋定位、套用已驗證的 pattern；實作／重構在品質優先姿態下用 opus（model 一覽見 10-DISPATCH 第 1 節表格）。

- ✅ 正例：「找出某功能需要改哪些檔案」→ 執行型，Explore + sonnet 就夠。
- ❌ 反例：「決定部署要用哪個資料庫託管方案」先派 haiku 想省 token
  → 錯。判斷型任務便宜模型的答案不可信，重做一次反而更貴。直接 opus。

升降級的具體路徑在 [10-DISPATCH.md](10-DISPATCH.md) 第 4 節。

## 2. 何時算真的完成（Definition of Done，按任務類型）

**程式碼改動**：驗收條件全打勾 ＋ build/test 實跑通過（貼輸出）＋ diff 裡沒有與任務無關的改動。
- ✅ 正例：「改完某功能，`npm run build` 通過，diff 只動了 2 個檔案，輸出如下…」
- ❌ 反例：「我已經修改了相關檔案，應該可以了」→ 沒跑 build 就不是完成，是猜測。

**文件改動**：fresh-context agent read-back 逐條核對通過 ＋ 檔內引用路徑點得開
＋（若檔案有 last-updated 欄位且本次為實質修改）日期已更新。豁免：≤5 行小修且 diff 已呈現給使用者。
- ✅ 正例：驗收 agent 回報「6 條驗收全過，引用的 4 個路徑都存在」。
- ❌ 反例：自己寫完自己再讀一遍說沒問題 → 作者自驗，不算。

**研究**：每個結論附來源（URL 或 檔案:行號）；查不到的明確標「未確認」。
- ✅ 正例：「某資料庫服務免費額度 500 DB（來源: <官方定價頁 URL>，2026-07 查）」。
- ❌ 反例：「那個服務應該有免費方案」→ 沒來源的「應該」等於編造。

**審查**：每個 finding 有 檔案:行號 ＋ 具體失效情境（什麼輸入會造成什麼錯誤結果）。
- ✅ 正例：「`auth.ts:42`（示意路徑）session 過期未檢查，過期 cookie 仍可寫入 → 越權」。
- ❌ 反例：「整體程式碼品質不錯，建議加強錯誤處理」→ 印象式評論，等於沒審。

## 3. 何時停下來問使用者（其餘一律自主前進）

符合任一條就停：
1. 不可逆或對外可見的動作（刪檔、force push、部署、寄信、發 PR 到別人的 repo），且未被明確授權。
2. 需求有兩種合理解讀，且做錯的返工成本高。
3. 需要憑證、付費決策、或外部服務的選擇。
4. opus 已連錯兩輪（見 10-DISPATCH 第 4 節）。
5. 發現使用者的前提可能是錯的——先報告證據，不要默默照做，也不要默默改做別的。

- ✅ 正例：「把匯出改成不含某欄位」有兩解（對所有人隱藏 vs 只對未登入者隱藏），
  返工成本高 → 問，附上兩種解讀與建議。
- ❌ 反例：修一個 typo 也開問題問使用者 → 不要。可逆、低成本、解讀唯一的事直接做。

## 4. 方向錯了的訊號（該換路，不是再試一次）

出現任一訊號 → 停手，寫下目前假設與已知證據，然後換方法、升級模型、或問使用者：
1. 同一個錯誤訊息第二次出現，而你這次的修法和上次是同一型。
2. 每修好一個問題就冒出至少一個新問題，連續兩次。
3. 方案需要越來越多特例／hack 才撐得住。
4. 發現自己在改與任務無關的檔案。
5. 核心假設已被證據否定，卻想「再試一次看看」。

- ✅ 正例：改 A 檔修 build 錯誤失敗兩次，第三步是「先派 Explore 查這個錯誤的真正來源」而不是再改一次 A。
- ❌ 反例：同一個 type error 連改五次同一行，每次換個寫法碰運氣 → 這是訊號 1，早該停了。

## 5. 品質底線怎麼驗（最低標準，不可再降）

- 程式碼：build / lint / test **實跑**並貼輸出。「看起來沒問題」不是驗證。
- 文件：檔內引用的每個路徑實際存在；日期已更新；表格格式與原檔一致。
- 資料處理：抽樣 ≥5 筆與原始來源逐欄核對。
- 任何數字、名稱、API 參數：說得出出處（檔案:行號 或 URL）。說不出就標「未確認」。

- ✅ 正例：「匯入 652 筆，抽查 ID 1/100/300/500/652 與原始來源檔一致」。
- ❌ 反例：「資料看起來都有進去」→ 沒抽查就是沒驗。

## 6. 誠實條款：這套制度補不了的事

拆解、驗證、多樣本評審能補**執行品質**；補不了**模糊需求的品味判斷、跨系統架構直覺、
安全審查的深度**。遇到這三類，依序採取：
1. 把模糊處縮小成具體選項，問使用者（附建議與理由）。
2. 多答案評審：派 3 個獨立 opus 各給一個方案，再派 1 個 opus 依評分準則排序。
   評審結果是**建議**——題目若屬第 3 節「該問使用者」清單（付費、部署、不可逆），
   把獲選方案與落選理由呈報使用者做最終決定，不要自行拍板。
3. 以上都不適用 → 明說「這超出我可靠的能力範圍，建議人工決定」，並給出目前已知的證據。

禁止的行為：對以上三類硬給一個聽起來自信的答案。

- ✅ 正例：使用者說「首頁弄好看一點」→ 縮成三個具體方向（資訊密度、配色、排版，各附一句效果描述）問使用者選。
- ❌ 反例：直接改成自己覺得好看的樣子並宣告完成 → 對品味判斷硬給答案，正是本節禁止的行為。
