# 派工 Prompt 模板
<!-- last-updated: 2026-07-18 | 用法：複製對應模板 → 填掉所有 <...> → 用 Agent tool 派出。 -->
<!-- 除最後的 read-back 驗收模板（刻意不含動機與脈絡，見 10-DISPATCH 第 2 節例外）外，每份模板已內建三件套（目標與動機／驗收條件／回報格式）與回報合約。不要刪驗收條件來省字。 -->

通則：
- **`subagent_type` 優先用 `~/.claude/agents/` 具名定義檔**（實作／重構→`implementer`、研究→`researcher`、審查→`reviewer`、read-back 驗收→`verifier`、機械批次套用→`bulk-editor`、大檔/log 抽取→`log-digger`、搜尋→`Explore`）；模板內標的 `general-purpose` 是**該 session 無對應定義檔時的 fallback**（報 `Agent type not found` 即退回，見 10-DISPATCH 第 0 節）。具名 agent 自帶額外紀律（implementer 強制實跑 build 貼輸出、verifier 唯讀 fresh-context），模板其餘欄位（動機／驗收條件／回報格式）照填不變。(verified 2026-07-18)
- 互相獨立的派工在同一則訊息一次派出（並行）。
- `<動機>` 一定要填——agent 靠它在邊界情況自行取捨，不填就會回來問或亂猜。
- 模板結尾那句「你的最終訊息就是全部回報」不可刪，刪了 agent 會以為有人能追問。
- 實作／重構模板裡作者跑 build 屬**自查**；主對話收到回報後複跑同一指令即完成驗收，
  不必另派 agent（依據：10-DISPATCH 第 5 節）。

---

## 1. 搜尋／定位（subagent_type: `Explore`, model: `sonnet`）

```
目標：找出 <要找什麼，例：某頁面欄位在前端所有的渲染位置>。
動機：<主任務為何需要，例：接下來要在未登入時隱藏該欄，需要完整清單以免漏改>。
範圍：<目錄／檔案類型，例：前端目錄內的 .tsx 與 .ts>。
已知線索：<關鍵字、命名慣例，例：關鍵字 "fieldName"、某 Table 元件>。
驗收條件：
- 每個結果附 檔案:行號。
- 每個結果一句話說明與目標的關聯。
- 找不到也要回報：搜了哪些目錄、用了哪些關鍵字。
回報格式：結論 ≤10 行 ＋ 檔案:行號 清單。不要貼大段程式碼原文。
你的最終訊息就是全部回報，沒有人會追問。
```

## 2. 實作（subagent_type: `general-purpose`, model: `opus`）

```
目標：<要實作什麼，具體到可驗收>。
動機：<為什麼要做、使用者真正想要的效果>。
脈絡：<相關檔案:行號、既有慣例、前一步的結論>。
限制：只改與任務直接相關的檔案；跟隨既有程式風格；不做未要求的「順手改善」。
驗收條件：
- <功能條件 1、2、…>
- `<build/test 指令，例：cd <你的專案> && npm run build>` 通過。
- diff 中每一行都能對應到本任務。
回報格式：改了哪些檔案（檔案:行號）、如何驗證的（貼指令輸出重點）、已知風險或未處理事項。
你的最終訊息就是全部回報，沒有人會追問。
```

## 3. 重構（subagent_type: `general-purpose`, model: `opus`）

```
目標：重構 <對象>，行為不得改變。
動機：<為什麼值得重構>。
安全網：先跑 `<test/build 指令>` 記錄基準結果；重構後必須得到相同結果。
限制：不改公開介面（除非任務明說）；不順手改無關程式；一次一個重構主題。
驗收條件：
- 重構前後 test/build 結果一致（兩次輸出都要貼重點）。
- 無孤兒：被你改動而不再使用的 import／變數／函式已移除。
回報格式：改動摘要、前後驗證輸出、任何行為疑似改變之處（若有，標為風險）。
你的最終訊息就是全部回報，沒有人會追問。
```

## 4. 研究（subagent_type: `general-purpose`, model: `opus`）

```
目標：回答 <具體問題>。
動機：<這個答案將決定什麼>。
要求：
- 每個結論附來源（URL 或 檔案:行號）與查證日期。
- 區分「事實（有來源）」與「推論（你的判斷）」，分開標示。
- 查不到的部分明確寫「未確認」，不要補完。
驗收條件：上述三點全部做到；若答案影響重大決策，額外列出反方證據。
回報格式：結論 ≤10 行；來源清單；未確認事項。長篇整理寫到 <檔案路徑> 回傳路徑即可。
你的最終訊息就是全部回報，沒有人會追問。
```

## 5. 審查（subagent_type: `general-purpose`, model: `opus`）
<!-- 審查本 repo working diff 時，優先用現成的 /code-review skill，不要用這份模板重造。 -->
<!-- 這份模板用於：審查指定檔案、文件、或 skill 覆蓋不到的範圍。 -->

```
目標：審查 <對象：檔案路徑或 diff 範圍>，找 <重點：正確性 bug／安全問題／與規格不符>。
動機：<為什麼現在審、後果是什麼>。
要求：
- 每個 finding：檔案:行號 ＋ 一句話缺陷描述 ＋ 具體失效情境（什麼輸入導致什麼錯誤結果）。
- 按嚴重度排序。沒把握的標 PLAUSIBLE，有把握的標 CONFIRMED。
- 禁止印象式評論（「品質不錯」「建議加強」）與未被要求的 style 意見。
驗收條件：每個 finding 都可依 檔案:行號 直接定位；失效情境具體可重現。
回報格式：finding 清單（嚴重度排序）；最後一行寫「共 N 個 finding，其中 M 個 CONFIRMED」。
找不到問題就回報「無 finding」＋ 你檢查過哪些面向。
你的最終訊息就是全部回報，沒有人會追問。
```

## 驗收派工（配合 10-DISPATCH 第 5 節「驗證不自驗」）

read-back 驗收（subagent_type: `general-purpose`, model: `opus`；受驗檔 ≤100 行可用 `sonnet`）：

```
目標：驗收檔案 <路徑>。你是 fresh-context 驗收者，之前的工作過程與你無關。
逐條核對以下驗收條件，每條回報 過／不過 ＋ 證據（引用檔案內容的行號）：
1. <條件一>
2. <條件二>
…
另外檢查：檔內引用的路徑是否都存在；若檔案有 last-updated 欄位且本次為實質修改，日期是否已更新；有無明顯缺漏段落。
回報格式：逐條 過／不過 清單 ＋ 總結一行。不過的條目要說明缺什麼。
你的最終訊息就是全部回報，沒有人會追問。
```
