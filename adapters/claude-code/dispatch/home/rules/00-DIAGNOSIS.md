# 快速診斷：本 harness 的三大失效模式
<!-- last-updated: 2026-07-03 | 建立者: Fable 5 建制 session | 所有 rules 檔的設計依據 -->

依據 2026-07-03 對原始機器的實際盤點（settings、repo 內容、工具 schema、記憶機制）。
後面每一份制度檔都是為了修這三件事。閱讀順序：先看修法指向的檔案，不用背下本檔。

---

## 1. Token 漏最兇：主對話親自讀大檔、掃 repo

**症狀**：主對話直接 Read 整份長文件、grep 全 repo 把原始結果倒進 context、翻 log。
context 一滿就觸發摘要壓縮，最早的使用者指示最先被壓掉，session 後半段開始跑偏——
這同時是 token 洩漏和失焦的共同根源。

**原始機器上的實例**（採用時對照你自己的環境）：某專案內有 500KB 級的 xlsx、20K 的
設計文件、整個前端 submodule；一次「順手看一下」就是數千 token 進主對話。

**修法**（已制度化在 [10-DISPATCH.md](10-DISPATCH.md) 第 1 節）：
- 讀超過 200 行、超過 3 個檔案、或位置不確定的搜尋 → 派 subagent，主對話只收結論與 檔案:行號。
- xlsx / 圖片 / log 這類大檔永遠不直接讀，派 agent 用 script 抽出需要的部分。

---

## 2. 最容易失焦：指示檔案腐化且互相矛盾

**症狀**：弱模型把過時文件當成現況、在重複或衝突的規則之間隨機挑一條遵守。

**原始機器上的實例**（採用時對照你自己的環境）：
- 一份 guideline 文件整段內容重複貼了兩次（前半與後半幾乎相同），閱讀時差點當成兩段不同指示。
- 舊 CLAUDE.md 是通用行為守則，沒有任何專案事實；專案事實散落在多份文件（規格／計畫／
  票務）且彼此有出入（計畫文件估 ~661 筆資料、實際 652 筆——規格文件已註記，計畫文件沒改）。

**修法**：
- 單一事實源：CLAUDE.md 只做路由；專案現況只認 FEATURE.md 與 code 本身，
  PLAN / MEETING / RECOMMEND 視為歷史文件（權威順序寫在專案 CLAUDE.md）。
- 每個制度檔標 `last-updated`；發現規則與現實不符，照 [40-MAINTENANCE.md](40-MAINTENANCE.md) 立即修（先備份）。

---

## 3. 最容易出錯：自我宣告完成、無外部驗證

**症狀**：改完就說「完成」——沒 build、沒測試、沒讓第二雙眼睛看過；或檔案寫了但內容缺漏、
路徑失效。作者自己驗自己，永遠驗得過。

**原始機器上的實例**（採用時對照你自己的環境）：舊 CLAUDE.md 有「Goal-Driven Execution」
的精神條款，但沒有任何可執行的驗收機制；環境內也沒有強制驗證的 hook。

**修法**（已制度化在 [20-JUDGMENT.md](20-JUDGMENT.md) 第 2 節與 [10-DISPATCH.md](10-DISPATCH.md) 第 5 節）：
- 程式碼：宣告完成前必跑 build / test（例：`cd <你的專案> && npm run build`），貼結果。
- 文件：派 fresh-context agent read-back，拿驗收條件逐條核對。
- 高風險判斷：第二意見——獨立 agent 用同樣輸入重答，分歧就呈報使用者。
