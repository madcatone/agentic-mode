# REPORT-PROTOCOL — 派工回報協議

每個被派工的 agent，最終訊息必須是**完整回報**（沒有人會追問），依下列段落結構撰寫。
段落標記（①…⑥）供機械評分 grep，**標題字元照抄**。

## 必要段落

- **① 產出清單**：新增/修改檔案（含行數或 +/- 概數）；無檔案產出的任務改列「動作清單」。
- **② 關鍵內容摘要**：做了什麼、核心結論；事實與你的推論分開標示。
- **③ 機械驗證輸出**：本 repo 機械 gate 指令的最終輸出**原文**（如 gate 的 summary 行）；沒跑＝沒完成。
- **④ 偏差與未盡項**：與任務書的每一處偏離、繞過、未完成——如實列，禁止美化。
  不確定＝尚未完成；禁止因預算把未完成標記為完成。
- **⑤ 過程要點**（可選但建議）：關鍵決策點與取捨理由，供裁決者快速抽查。
- **⑥ 指示摩擦（instruction friction）——進化信號通道，認真填**：
  - 哪句指示你讀了不只一遍才懂，或理解成了別的意思？
  - 哪條驗收條件你不確定「怎樣才算過」？
  - 若允許你改自己的任務書，你會改哪一行、怎麼改？
  - 本次執行中什麼工具/環境行為出乎你意料？
  沒有摩擦就明寫「⑥ 無」——但連續多次「無」而 run 又出問題，會被視為填寫不誠實。

## 誠實條款

- 引用原文：每處 ≤25 詞、至多兩個短句；引註標示如實（句數/詞數不虛報）。
- 查不到的寫「未確認」；身分/來源存疑的標注存疑。
- 回報是給**沒看過你工作過程的人**讀的——自足、可獨立核驗。

## 這些報告去哪了（你為什麼要認真寫）

回報＋⑥ 會進入教練迴圈：指揮官（或更強模型）批次審閱 → 產出 patch（規則、腳本、模板）→
每條 patch 引用觸發它的報告 → 你下次拿到的任務書因此更清楚。**你寫得越誠實，系統對你越好用。**
