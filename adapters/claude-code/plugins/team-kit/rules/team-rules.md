# team-kit 規範（team-rules）

<!-- last-updated: 2026-10-17 | 初版：蒸餾自課堂 team-kit（HWDC-2026），措辭全數重寫，僅保留規則編號骨架與語義 -->

本檔是個人 team-kit（observer／coder／reviewer／fortify 四角色）的**規範單一來源**：
所有 skill 與角色指引以規則編號（如 `TEST-06`、`SEC-03`）**引用**本檔，不各自重寫標準；
修訂規則只改本檔，引用處自動跟隨。規則本體語言中立，不假設特定語言、框架或規格系統；
語言／框架特定的做法只作為例子出現，以「例：」標明，不構成規則本體。

## 使用方式

- **分級三級**（每條規則行尾標記）：
  - `必要`：違反即為阻擋問題（blocking），未解決不通過審查。
  - `建議`：不阻擋；提出時必須附具體影響（耦合、維護成本、失敗情境），不依個人偏好。
  - `涉及時`：僅當規則標明的條件成立時適用，成立時效力同 `必要`；
    條件不成立時標「不適用」，不是違規。
- **來源標記**：行尾 `（來源: <來源檔>:<規則編號>｜分級: <級別>）`。
  `來源` 為借用出處（蒸餾自課堂 team-kit 對應檔案，措辭已重寫）或 `新增`。
- 四角色一體適用：coder 對照 CORE／CODE／TEST／SEC 實作；reviewer 與 fortify 依同表檢查；
  observer 釐清任務時引用 CORE-01 與「既有系統與例外」章。

## 行為準則（CORE）

所有角色共用的工作紀律；其他章定義「程式要做到什麼」，這章定義「工作時的行為」。

- **CORE-01｜先想清楚再寫**：動手前寫下本次工作的假設。需求有多種解讀時列出各解讀並詢問，
  不自行挑一種；發現更簡單的做法時提出；缺少關鍵資訊時回報 BLOCKED，不靠猜測補齊。
  （來源: core-principles.md:CORE-01｜分級: 必要）
- **CORE-02｜簡單優先**：只寫完成本次任務所需的程式——不加未要求的功能、只用一次的抽象、
  未要求的可設定性，也不替不可能發生的情境寫錯誤處理。判準：資深工程師看了會不會覺得過度複雜。
  （來源: core-principles.md:CORE-02｜分級: 必要）
- **CORE-03｜精準修改**：只改本次任務或 finding 需要的地方；不順手改相鄰的程式、註解或格式，
  不重構可正常運作的程式，沿用既有風格。與本次無關的死碼在回報中提出、不直接刪除；
  自己本次改動造成不再使用的 import、變數或函式要一併移除。
  判準：每一行變更都能對回本次的任務或 finding。
  （來源: core-principles.md:CORE-03｜分級: 必要）
- **CORE-04｜以可驗證的目標推進**：先把任務轉成可驗證的成功條件再動手——修缺陷先寫能重現
  問題的測試再讓它通過；重構前後既有測試都要通過；多步驟任務先列簡短計畫與每步的驗證方式。
  驗證沒有通過，不宣告完成。
  （來源: core-principles.md:CORE-04｜分級: 必要）

### 由誰檢查

| 規則 | 檢查方式 |
|---|---|
| CORE-01 | observer 釐清任務時列出歧義並詢問；coder 遇規格歧義回報 BLOCKED；reviewer 發現程式行為來自未經確認的假設時提 finding |
| CORE-02 | reviewer 對照任務範圍：未要求的功能、設定或抽象為阻擋問題；寫法可再簡化但不影響需求時，列為非阻擋建議 |
| CORE-03 | reviewer 以 diff 對照任務與 findings，找不到對應依據的變更為阻擋問題 |
| CORE-04 | 以專案 build／test 指令的實跑輸出與 TEST 章為準；任務的接受條件要有對應測試 |

（表來源: core-principles.md:由誰檢查——角色名對應本 kit 的 observer／coder／reviewer／fortify）

## 程式品質（CODE）

- **CODE-01｜變更限於核准範圍**：變更限於本次核准的任務；保持既有公開契約及行為，
  除非任務明確核准改變。依既有專案風格實作，不順便加入無關框架或大幅重構。
  （來源: code-quality.md:CODE-01｜分級: 必要）
- **CODE-02（涉及 I/O 時）｜非同步不阻塞**：I/O 作業採該技術棧慣用的非同步／非阻塞模式，
  不在關鍵流程同步等待非同步結果（例：以同步取值屬性阻塞 task）；支援取消的呼叫
  正確傳遞取消機制，不把取消當正常成功。
  （來源: code-quality.md:CODE-02｜分級: 涉及時）
- **CODE-03｜錯誤處理誠實**：區分預期業務拒絕與非預期系統失敗，結果契約清楚；
  禁止 catch 後吞掉例外、回報假成功或遺失原始錯誤資訊，重拋時保留原始堆疊。
  （來源: code-quality.md:CODE-03｜分級: 必要）
- **CODE-04｜資源與邊界**：正確處理可空值、邊界條件與資源生命週期；資源依擁有權明確釋放
  （例：實作 dispose／async-dispose 契約的物件由擁有者釋放）；禁止生命週期不明的可變全域／static 狀態。
  （來源: code-quality.md:CODE-04｜分級: 必要）
- **CODE-05（共享狀態時）｜並行安全**：明確處理並行安全與一致性；不得只因單人操作測試成功
  就假設共享資源安全。具體並行行為由任務／設計確認。
  （來源: code-quality.md:CODE-05｜分級: 涉及時）
- **CODE-06｜日誌有意義**：日誌採結構化資訊與適當等級，不得以大量無關輸出掩蓋失敗；
  機密與錯誤資訊的處理依 SEC 章辦理。
  （來源: code-quality.md:CODE-06｜分級: 必要）
- **CODE-07｜零新警告**：本次變更不得引入新的編譯器／linter／analyzer 診斷；有既有警告時
  在回報中說明基線。禁止關閉分析器、抑制警告或調降門檻換取綠燈（例：NoWarn 類開關、
  廣域抑制註解）；調整建置／分析組態屬政策變更，須明確核准。
  （來源: code-quality.md:CODE-07｜分級: 必要）
- **CODE-08｜消除高影響重複**：消除**影響本次正確性或維護性**的重複邏輯、過深分支與
  多重責任；提出時附具體影響，不依個人偏好要求抽象化。
  （來源: code-quality.md:CODE-08｜分級: 建議）

## 測試（TEST）

- **TEST-01｜接受條件對應測試**：把本次任務的接受條件逐條對應到實際測試與 assertion，
  涵蓋成功、拒絕、邊界及受影響的既有行為。測試名稱及數量不能代替證據。
  （來源: testing.md:TEST-01｜分級: 必要）
- **TEST-02｜測試層次依變更責任**：核心業務規則以單元測試直接驗證；用例協調邏輯測流程
  與介面互動，必要時以 test double 隔離依賴；涉及外部系統（資料庫、網路、檔案）的行為
  以適當的整合測試涵蓋。測試選擇依變更責任，不要求每次修改都重建所有層次。
  （來源: testing.md:TEST-02｜分級: 必要）
- **TEST-03｜回歸測試**：修復缺陷時加入能重現原問題的回歸測試；重構須保留既有外部行為
  的測試證據；新需求的具體期望由任務定義。
  （來源: testing.md:TEST-03｜分級: 必要）
- **TEST-04｜測試可重現**：測試可重複、隔離，不依賴執行順序、共享前次資料或未控制的外部
  服務；測試須有實質 assertion，禁止空白範本測試。
  （來源: testing.md:TEST-04｜分級: 必要）
- **TEST-05（涉及安全機制時）｜真實防護路徑**：測試真實保護機制及正常／拒絕路徑；
  不得停用授權、驗證、編碼等機制來讓測試通過。
  （來源: testing.md:TEST-05｜分級: 涉及時）
- **TEST-06｜實跑為證**：直接執行專案的 build／test 指令，閱讀當次輸出與測試摘要；
  失敗、零測試、未執行或略過的測試都不能當作 PASS 交付。
  （來源: testing.md:TEST-06｜分級: 必要）
- **TEST-07｜不得弱化測試**：禁止刪除、跳過或弱化測試來消除 FAIL；若接受條件確實改變，
  先重新確認需求，再同步修改測試並說明原因。
  （來源: testing.md:TEST-07｜分級: 必要）

檢查分工：執行結果證明程式能建置、測試有執行且通過（TEST-06）；reviewer 確認測試
是否真的驗證需求（TEST-01）。全綠不表示接受條件已完整涵蓋。

## 安全（SEC）

適用範圍：只按本次變更及相關設定檢查；不存在的 SQL、檔案或外部呼叫不虛構 finding。
標 `涉及時` 的規則在條件不成立時（例：非 web 專案之於 SEC-06／SEC-11 的瀏覽器情境）
標「不適用」，不是違規。

- **SEC-01｜秘密不進原碼**：禁止將憑證、密碼、auth key、token 或私鑰寫入原碼、提交的設定
  或日誌；使用環境與平台支援的秘密管理。占位字串不等於真實洩漏，但範例不得鼓勵硬編碼。
  （來源: security.md:SEC-01｜分級: 必要）
- **SEC-02｜輸入驗證、輸出編碼**：不可信輸入先驗證；輸出依實際上下文（HTML、attribute、
  JavaScript、URL 等）編碼；禁止未經明確清理策略的原始 HTML 輸出。
  （來源: security.md:SEC-02｜分級: 必要）
- **SEC-03（涉及資料庫時）｜查詢參數化**：使用參數化操作，禁止將不可信值拼接成 SQL；
  查詢參數化不能代替物件存取授權（見 SEC-05）。
  （來源: security.md:SEC-03｜分級: 涉及時）
- **SEC-04（涉及檔案／URL／程序時）｜邊界控制**：控制允許的路徑與目的地，防止越界存取、
  SSRF、open redirect 及命令注入；不得以不可信字串組合 shell 命令。
  （來源: security.md:SEC-04｜分級: 涉及時）
- **SEC-05｜授權邊界**：依任務／設計交代的使用者、權限與部署邊界驗證操作及物件存取；
  涉及多租戶時驗證租戶隔離。未交代必要的存取邊界時先釐清，不能自行假定任何人可操作。
  （來源: security.md:SEC-05｜分級: 必要）
- **SEC-06（瀏覽器自動攜帶憑證的狀態變更時）｜跨站請求防護**：狀態變更請求須有跨站請求
  偽造（CSRF）防護——採用框架內建的反偽造 token 機制（例：表單 antiforgery token）；
  安全方法（GET）不改變業務狀態。其他認證方式按實際威脅模型判斷，不把所有 API
  當成 cookie 表單。
  （來源: security.md:SEC-06｜分級: 涉及時）
- **SEC-07｜輸入綁定白名單**：僅綁定允許修改的輸入欄位；權限、擁有者與受控狀態由伺服器
  判定，禁止直接以持久層物件作為輸入綁定目標造成大量指定（overposting）。
  （來源: security.md:SEC-07｜分級: 必要）
- **SEC-08｜錯誤不洩密**：錯誤回應不洩漏 stack trace、連線字串、內部路徑或秘密；
  日誌與監控只保留必要且經處理的敏感資料。
  （來源: security.md:SEC-08｜分級: 必要）
- **SEC-09（涉及密碼學時）｜標準演算法與安全亂數**：密碼學與隨機數僅使用受支援的標準
  函式庫與當前公認安全的演算法。判準：
  - 安全用途的隨機值（token、重設碼、金鑰）使用密碼學安全亂數產生器
    （例：.NET RandomNumberGenerator），不用一般 PRNG 或 GUID。
  - 安全用途的雜湊不用 MD5、SHA-1；密碼使用專用密碼雜湊器。
  - 對稱加密不用已知弱化的演算法或模式（例：DES、RC2、ECB 模式、固定 IV）。
  - XML 類解析停用 DTD 與外部實體；反序列化不依輸入決定型別。
  - 上傳檔案及資源依實際用途限制型別、大小與處理成本。
  （來源: security.md:SEC-09｜分級: 涉及時）
- **SEC-10（涉及日誌時）｜日誌鍛造防護**：不可信輸入寫入日誌時以日誌 API 的結構化參數
  機制傳值（例：訊息範本參數），不以字串串接或插值組訊息；可能含換行的值先移除或編碼
  CR、LF 等控制字元，避免偽造日誌紀錄。
  （來源: security.md:SEC-10｜分級: 涉及時）
- **SEC-11（設定 cookie／回應標頭／CORS 時）｜瀏覽器端安全屬性**：cookie 設 HttpOnly 與
  適當 SameSite，敏感 cookie 不持久化；部署邊界使用 HTTPS 時設 Secure。不可信輸入寫入
  回應標頭或 cookie 前先驗證並移除 CR、LF。CORS 只允許明確列出的來源，不用萬用字元
  或一律允許的判斷。
  （來源: security.md:SEC-11｜分級: 涉及時）
- **SEC-12（以正規表示式處理不可信輸入時）｜回溯阻斷防護**：設定比對逾時或使用無回溯
  （線性時間）引擎（例：.NET RegexOptions.NonBacktracking），避免回溯造成阻斷服務；
  不以不可信輸入作為 pattern。
  （來源: security.md:SEC-12｜分級: 涉及時）
- **SEC-13（依部署邊界）｜加密傳輸**：部署環境全程使用加密傳輸（HTTPS／TLS）——含入口
  的 HTTPS 重新導向與 HSTS（依平台建議的順序設定）、對外呼叫與資料庫連線。任務明定
  僅限本機明文開發時，SEC-13 與 SEC-11 的 Secure 要求列為不適用，並於審查註記正式
  部署前補上。
  （來源: security.md:SEC-13｜分級: 涉及時）

## 既有系統與例外

- **LEGACY-01｜技術債不擴大**：新增／修改的程式須符合本規範；未受本次變更影響的既有
  問題記為技術債，在回報中提出，不擅自擴大重構。
  （來源: architecture.md:§既有系統及例外｜分級: 必要）
- **LEGACY-02｜既有架構阻擋時回報**：既有架構使核准任務無法符合必要規則時，回報
  BLOCKED，不自行降低標準。
  （來源: architecture.md:§既有系統及例外｜分級: 必要）
- **LEGACY-03｜例外須確認並記錄**：例外須由使用者確認後才成立，記錄於本次回報：
  規則編號、原因、影響範圍、替代措施與後續處置。任務規格不會自行覆寫本規範，
  agent 也不能自行批准例外。
  （來源: architecture.md:§既有系統及例外｜分級: 必要）

## 命名精要

- **NAME-03｜領域用語一致**：程式與回報的領域用語與需求文件一致，同一概念不使用多個
  同義名稱；需求詞彙不清楚先確認，不得拿範例名詞代替當次領域。
  （來源: naming.md:NAME-03｜分級: 必要）
- **NAME-05｜避免泛稱**：避免無法表達實際責任的泛稱（例：Manager、Helper、Data、
  Process）；僅當名稱無法表達責任時提出具體替代，不對慣用框架名稱任意挑剔。
  （來源: naming.md:NAME-05｜分級: 建議）

## 查證與標記法

- **VERIFY-01｜三級查證標記**：引用外部來源的名稱或分類（工具規則分類、漏洞類別、
  API 名稱等）時標查證等級：
  - `已確認`：名稱存在，且在本脈絡的適用性已查證。
  - `名稱已確認`：名稱存在，適用性尚未查證。
  - `[需查證]`：名稱與適用性皆未查證。
  引用 `[需查證]` 項目時保留標記；查證有結果後更新標記。
  （來源: fortify-categories.md:查證標記法｜分級: 建議）
