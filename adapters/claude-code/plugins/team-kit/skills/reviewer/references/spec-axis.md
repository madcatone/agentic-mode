# Spec 軸程序——對票逐條驗收（做得對不對）

> 輸入：票全文（issue／任務描述）、repo 路徑、diff 錨點。輸出：SKILL.md §3 契約的 verdict（`reviewer: spec`）。
> 契約借自 two-axis-review（Spec 軸）：**票面只是線索，不是地面真相**——症狀常指錯層，label 會誤導；裁決一律以 diff 與 raw 證據為準。

## 1. 拆票

1. 把票拆成**逐條接受條件**：可勾稽的句子——要什麼行為、什麼邊界、什麼附帶物（測試、文件、設定）。每條編號 S1、S2…，在 Scope 段列全。
2. 票有歧義時**不自行裁決**：歧義影響個別條件判定 → 該條標「無法驗證」並列出各解讀；票整體無法解析 → `status: BLOCKED`（缺：可判讀的票）。
3. 隱含條件（票沒寫但任務不可分割的，如「不破壞既有行為」）可列，但須標「隱含」並說明推論依據；不把個人標準冒充票的要求。

## 2. 逐條驗收（缺／多／錯）

對每條接受條件，在 diff 與檔案現況找證據（取證紀律照 SKILL.md §4——自跑 git status／diff／log／show，不以作者清單代替），判定 **過／不過／無法驗證**：

- **缺**：要求沒做或做一半。特別盯「**平行路徑只修一條**」——同型入口／分支／呼叫點只改一處，其餘漏改等於沒修完。
- **多（scope creep）**：diff 裡有票沒要求的行為——**逐 hunk 讀 diff，不看 commit 標題**；載體型 commit（release／merge／整理）是重災區。
- **錯**：看起來做了但語意不對——對照票的期望行為逐條核（例：票要求折扣、實作算成加成＝錯，不是「做了一半」）。

判定規則：

- 證據以自跑取證為準；票面敘述與 diff 衝突時以 diff 為準，並在 finding 註明差異。
- 「不過」的條件即 finding（帶票條編號 S#），格式照 SKILL.md §3——`檔案:行號`＋失效情境＋severity＋CONFIRMED／PLAUSIBLE。
- 「無法驗證」的條件列 Limitations（缺什麼證據），不算 FAIL，但**不得默默當成過**。

## 3. status

- 所有條件過 → `PASS`（僅隱含條件的可議處 → 列 Limitations）。
- 任一條「不過」（缺／多／錯，經查證釘死或依 SKILL.md §3 紀律處理 PLAUSIBLE）→ `FAIL`。
- 票缺失／整體無法解析 → `BLOCKED`（聚合者不該把這情況派進來——SKILL.md §2 輸入先驗）。

## 4. 輸出

照 SKILL.md §3 契約出 verdict：`reviewer: spec`；Scope 段列票條總數與每條一句話；Findings 每條帶 S# 編號。
