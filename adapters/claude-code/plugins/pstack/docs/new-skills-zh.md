## in-your-own-words

### 規則

這個 skill 用 agent 自己的話重述使用者的目標，以及使用者要解的問題。它不加
計畫、不寫程式、不多問。寫完重述就停。重述就是全部輸出。

### 怎麼用

觸發：`/in-your-own-words`，或「先重述目標再開始」。

輸入：使用者的訊息，以及他們指到的討論串或規格。

例子。使用者貼了一份很長的 bug 報告，然後輸入 `/in-your-own-words`。agent
回覆目標（「搜尋回傳了別的筆記本裡的筆記」）和問題（「篩選器用的是帳號 id，
不是筆記本 id」）。它不開檔案。

預期輸出：一段目標重述，一段問題重述。`interrogate` 把這段重述當作意圖。

### 分析

長的要求會把目標藏起來，agent 就會去解旁邊那個問題。這個 skill 用來在雜亂的
討論串開頭，以及 `interrogate` 之前，把目標寫清楚。使用者已經寫了一句目標和
一個可判真偽的完成條件時，跳過它。它接在 `sharpen` 前面（先對過目標再改寫
prompt），也餵給 `figure-it-out`（那個 skill 需要可證偽的完成謂詞）。陷阱：
把重述當成可以開工的許可。這個 skill 停在重述。

## sharpen

### 規則

這個 skill 把任務變深，而不是變大，然後改寫 prompt。改寫之前依序做四件事：

1. 說出這個領域的頂尖專業人士在這裡會做、而使用者沒要求的事。
2. 指出那位專業人士會從哪一份原始材料開始，而不是從已消化過的摘要開始。
3. 指出他們會用的方法與工具。
4. 說出除了使用者與 agent 之外，什麼東西能顯示結果是對的。

改寫後的 prompt 要求 agent 把實驗能決定的選擇做成原型，並依觀察到的結果給
建議。實驗決定不了的選擇留給使用者。四點和改寫後的 prompt 寫完就停。不要做
那件任務。

### 怎麼用

觸發：`/sharpen`。

輸入：使用者正要送出的 prompt。

例子。使用者寫「給 feed 加快取」。`/sharpen` 回答四點（先量 feed 的瓶頸、從
正式環境的 trace 開始、用 benchmark checklist、profile 是外部的對證），然後
交回一份 prompt，要求做兩種快取形狀的原型並附前後數字。它不加快取。

預期輸出：四個編號要點，然後一份改寫後的 prompt。

### 分析

淺的 prompt 產生淺的 diff。這個 skill 把任務抬到專家真正會做的工作，同時不
加範圍。用在非瑣碎的 prompt 之前。錯字、已點名的一行修正、或已經寫明原始
材料與外部對證的 prompt，跳過它。它站在 `architect`、`arena`、
`figure-it-out` 前面。陷阱：把「更深」做成「更多功能」。深度是更好的起點和
一個真的檢查，不是更長的待辦。

## reframe

### 規則

這個 skill 教操作者他們正在做的東西的專家用詞，從解過同一形狀問題的鄰近領域
借詞，再用這些詞改寫描述。從操作者自己的檔案、程式與描述開始，不從摘要開始。

若描述可能指到不只一個問題，先列出它可能是的兩或三個問題。每一項給出那個
問題的一個術語，以及把它和其他問題分開的徵兆。然後教最可能那一個的用詞，並
說為什麼挑它。

接著：

1. 給 8 到 12 個術語，依「會把做出來的東西改多少」排序。每一個：詞、一句白話
   意思、它對上描述的哪一段、一個真的如此使用它的專案、論文或系統（附連結），
   以及它讓操作者可以向 agent 要求什麼。
2. 挑 2 或 3 個鄰近領域。每一個說什麼能搬過來、類比在哪裡斷、哪些詞會帶回來。
3. 指出操作者沒提到、但應該在意的事。
4. 用新的詞改寫描述。

每個連結都要打開，確認它確實那樣使用這個詞。確認不了的引用刪掉。排序後的
術語、鄰近領域、遺漏的關注點、以及改寫後的描述都寫完就停。不要灌水。

### 怎麼用

觸發：`/reframe`。

輸入：操作者的描述，加上它指到的檔案與程式。

例子。使用者說「一個會重試失敗工作的佇列」。這句話可能是 at-least-once
送達，也可能是 saga。agent 列出兩者，並給出分開它們的徵兆（重試同一件工作，
對上補償步驟），挑 at-least-once，教 8 個術語（idempotency key、dead letter
等）並附已打開的連結，點出兩個鄰近領域，然後改寫描述。它不實作佇列。

預期輸出：需要時的歧義清單、8 到 12 個術語、2 或 3 個領域、遺漏的關注點，
以及一份改寫後的描述。每個連結都打開過。

### 分析

人用日常用語描述系統，然後叫 agent 做出另一個東西。這個 skill 在設計開始前
把專家的名字放上那個東西。描述含糊、或可能是兩個已知問題時使用。程式庫已經
用標準術語、而且描述與那個術語一致時跳過。它餵給 `sharpen` 和 `architect`。
陷阱：沒打開的引用，以及改寫時加了範圍而不是只為同一範圍換名字。

## ketchup

### 規則

這個 skill 把使用者在輸入 `/ketchup` 之前最後一則訊息之後、這個對話裡發生的
事補上，並列出每一件還等他們決定的事。通知和 subagent 的結果不是他們的訊息。
這一輪是唯讀的：不改程式、不啟動 app 或工作、不張貼任何東西。圖只能源自對話
裡已經有的材料。

行動項是只有使用者能做的決定。agent 自己還能做的工作不是行動項。不要編造
決定。發生了什麼控制在 100 字以內，圖不算。每一項 30 字。每一項都留著。字數
不是把清單換成一個數字或一條連結的理由。

語氣：白話、短句、沒有行話。說對使用者改變了什麼。除非使用者需要某個雜湊、
檔案路徑、指令、建置編號或測試次數才能行動，否則省掉它們。

回覆有開場句、圖、摘要行、最多三行補充、以及行動項時就停。什麼都沒發生、也
沒有東西在等，就說一聲並停。

### 怎麼用

觸發：`/ketchup`。

輸入：目前這個對話。不需要其他參數。

例子。使用者在一段很長的實作之後回來，輸入 `/ketchup`。回覆以「有兩個 PR 等
你合併」開頭。它嵌入先前那一輪已經截到的畫面，用一句口語列出每個要求的結果，
然後給兩個行動項：合併索引修正（風險低，測試過了），以及為空狀態挑一個顏色。

預期輸出：一句開場、已經存在的內嵌圖、每個要求一行短摘要，然後是行動項，每項
含建議、對使用者的改變、證據與風險。

### 分析

很長的 agent 回合會把決定埋起來。這個 skill 讓使用者只靠回覆就能決定，不必
把追蹤捲回去。回到一個對話時使用。想要跨對話的歷史（這個套件沒有那個 skill）
或想要一份設計時跳過。它是 `ketchup-video` 在沒有轉檔工具時退回的文字路徑。
陷阱：把仍等使用者的事標成完成，或編造一張截圖。

## ketchup-video

### 規則

遵循 `ketchup`，只改一件事：用一段短的、無聲的橫向投影片影片呈現發生了什麼，
取代 ketchup 的摘要與圖。時間窗從使用者在 `/ketchup-video` 之前寫的最後一則
訊息開始。在 repo 之外撰寫並轉出影片，是 ketchup 唯讀規則的唯一例外。

用環境裡可用的投影片轉影片工具來轉檔。沒有這種工具時，跳過影片，用一行點出
缺的工具，並改給 `/ketchup` 的文字回覆。這個退路是移植時的改寫。上游假設
轉檔器存在。

投影片最多 10 張，每張一個重點，靠改同一張圖來推進。字幕十個字，放在投影片
下方的條裡，燒進影格。每張投影片停留的時間，至少是它新增字數每三個字一秒。
嵌入之前，以對話視窗的大小看每張投影片的一個影格，並用檔案裡的影格量停留
時間。在那個時間內讀不完的投影片要改、重轉、再查。

回覆是 ketchup 的開場句、嵌入的影片、一行 agent 自己還能做的工作，以及行動項。
轉檔失敗時，用一行說失敗，並且只給那些決定。

### 怎麼用

觸發：`/ketchup-video`。

輸入：目前這個對話，加上機器上的投影片轉影片工具。

例子。和 `/ketchup` 同一個回來的情境，但使用者輸入 `/ketchup-video`。agent
先寫使用者離開時該帶走的一句話，用對話裡已有的截圖草擬六張投影片，轉出
mp4，檢查每張的一個影格，然後以開場句、影片、以及兩個合併決定回覆。機器上
沒有轉檔器時，回覆是一行點名缺的工具，加上 `/ketchup` 的文字。

預期輸出：開場句、影片、剩餘工作的一行、行動項。或是點名工具的退路加上
ketchup 文字。

### 分析

有些改變看比讀容易。這個 skill 給那種情況，決定清單與 `ketchup` 相同。對話裡
已經有截圖或看得出的前後對比時使用。純函式庫、沒有東西可指，或只需要文字時
跳過。它依賴 `ketchup` 的時間窗、語氣與行動項。陷阱：用錄螢幕代替轉影格，或
字幕蓋住投影片。

## poteto-help

### 規則

回答關於這個套件所附 skill 的問題。交回一份使用者可以送出的 prompt，並連結
那個 skill 檔。不要開始工作。要求做事的訊息不是求助問題：點出 skill、給出
prompt、然後停。

目錄只列這 45 個已附的 skill。使用者點名這個套件沒有的 skill 時，直說，並改
指向最接近的已附 skill。不要把他們送去模式 skill、設定 skill、或個人規則檔。
這個目錄上限是移植時的改寫。上游列出整份收藏。

訊息沒有點出情境時，問一個選擇題（挑 skill、寫 prompt、修正跑歪的一輪、跟上
這個對話），並且只回答那一節。問題是關於證明一個變更、而專案沒有 `verify-*`
skill 時，提到 `/create-verification-skill`。問題是關於競爭或不變式時，提到
形式驗證那一對 skill。

答案、最多一個範例 prompt、以及檔案連結都寫完就停。

### 怎麼用

觸發：`/poteto-help`、「which skill」、「how do I use pstack」。

輸入：一個問題。不是一件任務。

例子。使用者問「哪個 skill 審查 PR 而且不改它？」回覆點名 `/interrogate`，
從 `references/recipes.md` 給一個 prompt，並連結
`skills/interrogate/SKILL.md`。它不審查那個 PR。

預期輸出：skill 名稱、程式碼區塊裡的一個 prompt、連結。只有使用者要求整張
地圖時才給整張地圖。

### 分析

這個套件是 45 道程序。這個 skill 讓使用者不必讀完每一份檔案就能挑一個。還
不知道 slash 名稱時使用。已經知道 skill、或要在這一輪把工作做完時跳過。
prompt 的寫法在 `references/prompting.md`。可複製的 prompt 在
`references/recipes.md`。陷阱：在求助這一輪裡開始任務，或推薦這個套件沒有的
skill。

## create-formal-verification-skill

### 規則

找出 repo 裡「破壞會傷害使用者、而且測試很少碰到那個破壞」的承諾。驗證它的
一個性質。留下一份下一個 agent 可以冷讀就跑的專案內 skill。

挑回答這個問題成本最低的工具。事件的壞順序，預設用 TLA+ 模型檢查器，語言不
限。程式本身的性質（記憶體安全、溢位、資料結構不變式）用跑在程式上的驗證器。
這個語言沒有驗證器可跑時，直說，用產生的輸入測真實程式，並且不要做那個函式的
手寫模型。

產生的 skill 必須對得上程式、必須能失敗（在一個被破壞的變體上展示每個性質
失敗）、對界限誠實、不靠工具也能讀、重跑便宜，並標出它涵蓋的檔案以及上次確認
這件事的 commit。有 frontmatter 才會註冊。不要為了讓目前的程式通過而放寬性質。
只有使用者要求時才改產品程式。

檢查若是 TLA+ 模型，告訴下一個 agent 用 `/statechart` 讀每一個結果，而且用
名字指它。不要把 statechart 的指令抄進產生的 skill。

證明它：在一個會打破該性質的暫用變更上，照產生的 skill 走一次。它必須抓到
那個破壞。丟掉暫用變更，並確認檢查回到出發點。沒跑過的 skill 是草稿。證明跑
完、交接寫完就停。之後的漂移指向
`/maintain-formal-verification-skill`。

### 怎麼用

觸發：`/create-formal-verification-skill`、「model-check this race」、「prove
this invariant」。

輸入：一個 repo，以及使用者點名的區域或 bug。否則 agent 從它觀察得到的目標裡
挑最強的一個。

例子。一個付款服務的重試可能重複扣款。agent 寫一個小的 TLA+ 模型，展示拿掉
idempotency 檢查時不變式失敗，把檢查放回去，在專案的 skills 目錄產生
`verify-charges/SKILL.md`，把那個 skill 跑一次，然後告訴使用者工具、界限、
指令，以及沒涵蓋的部分。

預期輸出：一份帶涵蓋紀錄與同步 commit 的專案內 skill，加上一段白話交接。暫用
的破壞已經不在。

### 分析

測試檢查有人寫下來的案例。這個 skill 給那些沒寫下來的案例：交錯、重試、剖析器、
不安全的程式。那裡的 bug 很貴、而且測試碰不到時使用。一般 UI 行為用
`create-verification-skill`（它驅動 app）。有便宜測試的一次性 bug 用 `tdd`。
`statechart` 讀 TLA+ 的結果。`maintain-formal-verification-skill` 在之後的
commit 裡讓模型保持為真。陷阱：一個從未被看到失敗的檢查，或一個審查者打不開
對應檔案的模型。

## maintain-formal-verification-skill

### 規則

在略過 verify skill 的 commit 之後，把形式檢查拉回與程式一致。只改驗證：模型、
harness、性質檔、以及 verify skill。只有使用者要求時才改產品程式。不要為了讓
檢查通過而放寬性質。

每個檢查一個結果：**in sync**、**updated**、**bug**、或 **blocked**。一個檢查
可以同時是 updated 和 bug。

步驟：

1. 依 verify skill 做的事找到它。一個都沒有就停，並指向
   `/create-formal-verification-skill`。
2. 任何編輯之前，每個檢查先跑一次。這裡的通過表示舊描述仍然成立。它不表示程式
   是對的。
3. 從同步 commit 讀涵蓋程式的每一個變更，包含重新命名，以及新寫入受保護狀態的
   程式。每個變更分類：沒有影響、驗證不再描述程式、承諾是故意改的（引用證據），
   或承諾可能被破壞。
4. 從程式更新，而且在重跑之前更新。不要照「怎樣才會通過」去修模型。
5. 重跑。通過時，用性質所防的方式破壞新程式，確認檢查抓到它，然後丟掉那個破壞。
   失敗時，把反例在真實程式上逐步重放。做不到的步驟表示驗證是錯的。做得到的
   步驟是 bug。
6. 只有你拉回來的檢查才更新同步 commit。把 verify skill 再跟一次，確認它的步驟
   仍然跑得起來。

報告寫完、而且驗證更新放在自己的變更裡（與任何產品修正分開）就停。

### 怎麼用

觸發：`/maintain-formal-verification-skill`、「is the model still true to the
code」，以及碰過已驗證程式的合併之後。

輸入：專案內的 verify skill，或使用者點名的那一個。

例子。三個 commit 把 `charge` 改名，並加了一條退款路徑。agent 跑舊模型（它仍
通過），讀那些 commit，更新模型讓退款成為一個步驟，在暫用複本上打破退款的
idempotency 檢查，看到檢查器抓到它，還原暫用複本，然後以結果 **updated** 與
新的同步 commit 報告。重放做得到的真正重複退款是結果 **bug**，並附上引入它的
commit。

預期輸出：每個檢查一個結果、讀過的 commit、驗證改了什麼與證據、重跑、用來證明
它仍能失敗的那個破壞，以及每個 bug 以程式自己的步驟寫出。

### 分析

一個仍然通過的過期模型比一個失敗的測試更糟，因為它看起來像證明。這個 skill
用來把漂移和 bug 分開。在涵蓋程式的合併與重構之後使用。verify skill 還不存在
時跳過，並改去建立第一個模型（用 `create-formal-verification-skill`）。它是那個
skill 的維護對，就像 `maintain-verification-skill` 是
`create-verification-skill` 的維護對。陷阱：在這一輪裡改產品程式，或在
blocked 的檢查上移動同步 commit。

## statechart

### 規則

檢查一個在狀態之間移動的系統的 TLA+ 模型，並把它畫成 Mermaid 狀態圖。報告給出
到每個打破規則的狀態的最短路徑。讀者決定行為對不對。

在 repo 之外的暫用資料夾工作。寫好 spec 與 config，然後從這個 skill 的目錄跑
`scripts/statechart`（一支會跑 TypeScript 的 POSIX shell script）。在原生
Windows 上，用 Node 22.18 到 22.x，或 Node 23.6 之後，跑那個 `.ts` 檔。第一次
執行會安裝 TLC 與 Java，並且需要網路。

把讀者同意的每條規則寫成 INVARIANT。不要為了讓規則成立而放寬它。沒有走出步驟的
狀態會打破 `NoDeadlock`，包含正確的結束狀態：加一個只在結束狀態為真、而且不改
任何東西的動作。

把需要判斷的部分放進 view 模組（`--view`）：狀態與箭頭上的詞、階段、顏色、標題。
圖保持在 20 條箭頭以內。bug 路徑上的每個狀態都留著。打破不同規則的兩個狀態保持
兩個狀態。隱藏步驟時，每個圖上的狀態都要從起點走得到，每個在模型裡有走出步驟的
狀態至少留一條箭頭，一條箭頭的步驟要嘛全藏、要嘛全留。

圖的預算是 500 個狀態。超過時只畫通往被打破規則的路徑。把 `chart.mmd` 以
mermaid 程式碼區塊顯示。圖檔用 `references/render.md` 點名的轉譯器。

讀者拿到每張圖、每個 bug 一行（規則、那句話、路徑）、模型沒涵蓋的部分、以及
重新產生檔案的指令時就停。模型描述的是程式時，把每條 bug 路徑對真實程式重放。
bug 沒有發生時，先把模型當成錯的，直到你證明模型本身有誤。

### 怎麼用

觸發：`/statechart`，或「把這個 bug 顯示成一條穿過狀態的路徑」。

輸入：一份 TLA+ spec，或一段由 agent 轉成 spec 的描述。讀者需要特定用詞時再加
view 模組。

例子。一個登入流程可以跳過第二因素。agent 在暫用資料夾寫 spec，跑 script，然後
回覆 mermaid 圖、一行「不變式 second factor：Login, Password, Home」，以及重建
檔案的指令。這條路徑接著以測試對真實的 handler 重放。

預期輸出：`chart.mmd`（狀態數在 500 以內，或有規則被打破時）、報告裡的最短路徑，
以及交接的那幾行。沒有規則被打破而且模型超過 500 個狀態時，沒有圖檔。報告仍列出
狀態數。

### 分析

模型檢查器傾印的反例很難讀。這個 skill 用讀者的話顯示最短路徑。用在產品流程、
協定、或服務，以及 `create-formal-verification-skill` 產出 TLA+ 模型的時候。
不是狀態機的性質跳過它（用那個 skill 已經選的驗證器）。有便宜本地測試的 bug 也
跳過。它消費模型。它不取代 `interrogate` 或 `tdd`。陷阱：標籤用了變數名、把兩條
被打破的規則併成一個狀態，以及把這個 skill 的指令列抄進另一個 skill（那些路徑
會隨機器改變）。
